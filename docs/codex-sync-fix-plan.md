# Refusion 联机同步修复方案

## 1. 目标与已确定的边界

修复物体同步、加入时世界初始化、场景切换及重连中的状态不一致，不能只靠提高限流阈值掩盖问题。

- **不修改死亡、伤害和服务器死亡配置逻辑**；“不死”已确认属于配置问题。
- 客户端与 relay 同步升级，使用 **协议版本 3、产品版本 0.3.0**，明确拒绝旧协议，不维护双传输路径。
- 继续使用独立 relay 和伪主机架构，不恢复 Steam，不实现真正的无客户端世界模拟或无缝主机迁移。
- 加入时缺少非必要物体模组且下载失败，允许**明确提示后的降级加入**；必需地图加载失败、实体登记损坏等协议错误不能冒充成功。
- 初始化覆盖已联网的场景物体、运行时生成物体、玩家和关联状态，不把整张地图的所有静态对象重新生成一遍。

## 2. 重建可靠传输与流量调度

### 统一传输实现

- 复用仓库内的 `D:\PROJECTS\refusion\LabFusion\dependencies\LiteNetLib`。客户端、relay 和测试共用同一份传输及协议源代码，不引入第二套可靠 UDP 算法，也不增加客户端部署所需的独立 DLL。
- 游戏消息改为**二进制封装 + 原始 Fusion 字节**，移除游戏数据路径的 JSON/Base64；控制消息可以保留 JSON 内容，但必须经连接内可靠通道发送。
- 保留 `NetworkLayer` 现有对外发送接口。版本号仍以 `D:\PROJECTS\refusion\LabFusion\src\Mod.cs` 中的 `FusionVersion` 为唯一来源，relay 在构建时读取该值，删除独立硬编码版本。
- 可靠控制使用通道 0；Fusion 可靠消息及补同步屏障使用通道 1，映射为 `ReliableOrdered`。不可靠数据保留不可靠语义，不能全部提升为可靠发送。
- 固定传输 MTU 为 1200 字节。可靠消息由 LiteNetLib 分片；单个重组消息上限 64KiB，并为 vendored 接收重组增加片数、并发数和内存边界检查。
- 大体积不可靠位姿及语音采用有界应用分片：最多 64 片、250ms 过期、每连接最多 32 个重组任务及 2MiB 重组内存。缺片即丢弃整帧，不重传过期实时数据。

### 身份与线程边界

- 连接握手建立 `NetPeer → ClientId/SmallID/UUID` 映射；入口身份来自连接记录，不能采用客户端自报的身份或服务器标志。
- 客户端只能向伪主机提交游戏消息；服务器广播、定向发送、场景控制仅允许当前伪主机发出。校验内层路由、通道及发送者，保留现有 Fusion 处理器的权限检查。
- 每次连接带独立连接代次，每次服务器会话带 `SessionEpoch`，场景相关消息另带 `SceneEpoch`。这些都是临时状态，不写入持久身份文件。
- 网络线程只做收发、解析、校验和排队；Unity 对象、实体登记及生命周期钩子始终在主线程执行。网络处理不依赖游戏加载期间的帧更新。

### 队列与限流

- 删除目前“每连接统一 500 包/秒、超出直接丢”的游戏消息策略，改为按字节调度。默认普通连接 1MiB/s、伪主机 4MiB/s，突发额度为两秒，可通过服务器配置调整。
- 可靠消息保持 FIFO，优先发送；达到预算时排队并对补同步生产端施加背压，**不能静默丢弃**。每连接待发送及在途可靠数据合计上限 8MiB；无法维持边界或连续 30 秒没有交付进展时，明确断开并记录原因。
- 玩家及物体位姿按“场景、发送者、消息类型、实体”合并为最新值，并保留递增序号以拒绝旧帧；不能用一个全局序列覆盖不同实体。语音使用独立短队列，过期后丢弃，不按位姿方式合并。
- 主线程每帧最多处理 256 条消息或消耗 2ms，余下消息留待下一帧。可靠队列不能因为位姿堆积而丢失。
- 主机广播和排除广播各发送一次 relay 指令，由 relay 扇出。主机本地副本在主线程处理，取消远程回环依赖，并确保本地只执行一次。
- 服务器查询改用 LiteNetLib 无连接查询；保留地址、UDP 端口及 HTTP 状态接口能力，HTTP JSON 仅作向后兼容的字段扩展。

## 3. 将加入改为可确认的世界初始化

### 明确加入状态

新增：

`TransportAccepted → FusionRegistered → SceneReady → CatchingUp → Ready / ReadyDegraded`

- 获得本地 `PlayerID` 只进入 `FusionRegistered`，不能表示世界初始化完成。
- 伪主机未完成场景加载时，已认证连接进入等待状态，不开始实体补同步。
- 加入者完成目标地图、延迟初始化及本地 rig 绑定后，发送携带场景代次的 `SceneReady`。
- 补同步期间限制该玩家的物体交互和生成操作，但不暂停所需的网络接收与状态应用；使用独立初始化状态，不覆盖游戏模式已有的控制锁。

### 实体清单与完成确认

新增 `CatchupId`，以及补同步开始、实体清单、应用结果、缺失请求和完成确认消息。

- `SceneReady` 后，主机捕获玩家与实体清单，包含实体 ID、创建类型、当前所有者及所有权修订号；分批发送，不再单凭连接响应触发一次不可检查的协程。
- 按**基础实体创建 → 依赖关系建立 → 详细状态应用**执行。基础实体先登记，再恢复约束、抓取、插槽等跨实体关系，最后补齐位姿、休眠/裁剪及组件状态。
- 创建成功必须等到实际生成/绑定回调结束后才确认，不能在开始异步生成时提前确认。
- 详细状态仍复用现有实体和组件 catchup 钩子；增加事务上下文及完成屏障，依赖回调尚未完成时不能宣布该阶段结束。
- 只有清单项均处于“已应用、已销毁或明确的内容缺失”状态，才允许完成加入。网络故障、空所有者和实体 ID 冲突不能归类为内容缺失。
- 补同步期间的创建、销毁及所有权变化作为有序增量保留，在基线之后应用；销毁使用墓碑取消待生成项，所有者变化则更新修订号并向最新所有者请求状态。
- 每两秒检查停滞项，最多三次定向修复请求；正常同步阶段连续 30 秒无进展则明确失败，不能无限半加入。场景加载最长等待 180 秒，内容下载连续 120 秒无进度则结束该下载等待。

### 缺失内容的降级策略

- 复用现有下载开关、黑名单及体积限制，不绕过内容安全设置。
- 非必要生成物下载失败，记录 Barcode、实体 ID 和原因，并显示缺失摘要，最终状态为 `ReadyDegraded`。
- 依赖缺失物体的约束和组件关系也明确标记缺失，清理等待回调，不能留下永远等待的任务。
- 下载后来成功时，仅在原会话和原场景仍有效、实体未被销毁的情况下补建，随后请求最新状态。
- 必需地图不可用或地图原生实体无法正确匹配时，以明确诊断结束加入，不能绑定到错误对象。

### 修复已确认的实体缺陷

- 本地创建与接收创建复用同一个补同步注册入口，保证主机首先同步的地图物体也有创建回调，并且只注册一次。
- 生成物的补同步读取**当前**所有者，不能捕获最初的 `ownerID`。
- 创建与修复请求按实体 ID 幂等处理；重复包及重复回执不再生成第二个物体。
- 普通可转移物体失去所有者时由主机接管并发布新所有权；玩家实体不接管，锁定实体遵守原有规则。
- 所有者相关处理增加合法性检查。遇到未知实体或所有者，触发受限修复或明确失败，不再空引用或无限打印位姿错误。

## 4. 统一场景生命周期与会话隔离

- 伪主机的 Fusion 场景加载指令是唯一加载来源；relay 缓存的场景信息只用于展示和等待加入状态，不再另行调用 `SetTargetScene()`。
- 同一次加载使用同一 `SceneEpoch`；真正换图或重载同一地图都会产生新代次。删除“相同 Barcode 在 30 秒内忽略”的静态去重，改为代次幂等判断。
- 新场景开始后，取消旧场景的快照、实体请求、依赖回调、实时分片及位姿缓存。客户端完成新场景后重新进行补同步。
- 断线时停止并释放旧连接实例，清空收发队列、重组缓冲和等待任务。DNS、下载、rig 加载及物体生成等异步回调必须校验捕获的连接/场景代次，过期结果不得登记到新会话。
- 重复握手和连接响应不得重复触发 `OnStartServer`、场景重载、玩家创建或全量 catchup。
- 保留“伪主机离开则重置会话”的当前策略，但通过可靠控制通知其他客户端，并清楚记录受影响人数与原因；不在本轮加入无缝主机迁移。
- 保留 UUID、封禁、管理员和现有持久配置；会话及场景代次不跨进程恢复。

## 5. 测试、可观测性与发布

### 自动化验证

增加不依赖 BONELAB 的 .NET 测试运行器，覆盖实际共享协议和传输代码：

- 在固定随机种子的丢包、乱序、重复及延迟代理下，验证可靠消息有序、去重和最终交付。
- 覆盖 64KiB 分片、实时分片过期、恶意长度/片数、身份冒用、错误路由和旧代次消息。
- 覆盖可靠队列背压、过载明确断开、位姿合并，以及主机广播本地只处理一次。
- 验证补同步状态机、重复创建、缺失项修复、所有权变更、销毁墓碑、降级完成和场景取消。
- 压力基线为 10 个连接、1,000 个已有实体、50 个持续运动实体；模拟客户端主线程暂停 10 秒，要求内存有界且不静默丢失可靠消息。

### 游戏内验收

使用两至三个真实客户端验证：

1. 主机先抓取/移动地图物体，其他人后加入，物体登记及位置一致。
2. A 生成物体、B 接管、C 后加入，三端所有者及位姿一致；A 离开后仍正常。
3. 后加入者能恢复已有生成物、NPC、休眠物体、约束、抓取及插槽状态。
4. 补同步期间生成、销毁、转移所有权或切图，不出现幽灵物体和旧场景物体。
5. 同地图快速重连、30 秒内重入及主动重载，均只执行必要的加载。
6. 缺失模组下载失败时能明确降级；不影响其他实体完成初始化。
7. 多物体运动及语音同时运行至少 20 分钟，无持续实体缺失、所有者空引用或可靠消息丢弃。

死亡行为只做配置正确情况下的回归，不修改其规则。

### 日志与上线

- 日志及 `/status` 增加连接阶段、会话/场景代次、补同步预计/完成/缺失数、队列字节、在途可靠数据、重传和实时数据丢弃统计。
- 超载日志区分位姿合并、语音过期、可靠背压和协议拒绝，采用聚合输出；不能再用一条限流警告代替实际丢弃计数。
- 实施顺序：**共享协议及测试 → 两端传输与调度 → 场景/连接代次 → 实体补同步与回归**，每阶段独立验证。
- 发布前备份 relay 配置及访问数据；客户端和服务器同时升级到 0.3.0/协议 3。旧版本明确提示版本不匹配，不尝试以新协议解释旧数据。
- 验收以“清单与状态能核对、可靠消息无静默丢失、失败可解释”为准，而不是仅以“能加入、看起来顺畅”为准。
